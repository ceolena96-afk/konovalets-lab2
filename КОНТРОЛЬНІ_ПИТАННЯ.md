# Відповіді на контрольні питання ЛР2

## 1. Чим відрізняється git merge від git rebase?

`git merge` об’єднує історії двох гілок. Якщо історії розійшлися, зазвичай створюється окремий коміт злиття; за можливості fast-forward покажчик гілки просто пересувається вперед.

`git rebase` повторно застосовує коміти поточної гілки поверх іншої основи. Історія стає лінійною, але перенесені коміти отримують нові хеші. Уже опубліковану спільну історію не слід переписувати без узгодження з іншими учасниками.

## 2. Як відкотити останній коміт?

Вибір залежить від того, чи потрібно зберегти зміни та чи опублікований коміт.

- `git reset --soft HEAD~1` — прибрати останній локальний коміт, зберігши його зміни в індексі.
- `git reset HEAD~1` — прибрати останній локальний коміт, залишивши зміни у файлах, але прибравши їх з індексу.
- `git revert HEAD` — створити новий коміт, який скасовує зміни останнього коміту. Це придатний спосіб для вже опублікованої спільної історії.

`git reset --hard HEAD~1` також відкидає зміни відстежуваних файлів у робочій папці та індексі; його не слід використовувати, якщо ці дані потрібно зберегти.

## 3. Що таке GitHub Pages і як його увімкнути?

GitHub Pages — сервіс публікації статичних сайтів з GitHub-репозиторію. Він підходить для HTML, CSS та клієнтського JavaScript; серверна логіка на кшталт PHP ним не виконується.

Для цього готового HTML/CSS-проєкту:

1. Завантажити файли в репозиторій; `index.html` має бути в корені.
2. Відкрити `Settings` → `Pages`.
3. У `Build and deployment` вибрати джерело `Deploy from a branch`.
4. Вибрати гілку `main`, папку `/(root)` і зберегти.
5. Дочекатися успішної публікації та відкрити адресу, яку покаже GitHub.

Після наступних змін у вибраній гілці GitHub запускає оновлення сайту.

Джерело налаштувань: [офіційна документація GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).
